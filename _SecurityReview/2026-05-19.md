# Security Review Report — food-ordering-system

- **実施日:** 2026-05-19
- **対象:** リポジトリ全体（`main` ブランチ時点のコードベース全件レビュー、差分レビューではない）
- **レビュー観点:** 高信頼度（confidence ≥ 8）かつ実害のあるセキュリティ脆弱性のみ
- **レビュー手法:** 静的レビュー（コード読解のみ。実行・動的検証は行っていない）

---

## Scope

レビュー対象として確認したファイル群:

- 全 Java ソース（`@RestController` / `@Controller`、`@Service`、`@Repository`、Kafka listener、messaging adapter、JPA エンティティ）

- `init-schema.sql` / `init-data.sql`
- ルートおよび各モジュールの `pom.xml`
- `infrastructure/kafka/` 配下の Kafka 設定・コンシューマ・プロデューサ
- Avro スキーマ定義

対象サービス:
- `order-service`
- `payment-service`
- `customer-service`
- `restaurant-service`（実装途中：`restaurant-domain-core` のみ）
- 共通モジュール `common/`、`infrastructure/kafka/`

---

## Executive Summary

**HIGH / MEDIUM severity かつ confidence ≥ 8 の脆弱性は検出されませんでした。**

DDD + ヘキサゴナルアーキテクチャの構造により、ユーザー入力が `UUID`・`BigDecimal` 等の強い型を介して JPA に到達する設計になっており、注入系の典型的なシンクは構造的に存在しません。

ただし、デプロイ前に対処が必要なアーキテクチャ上のギャップを **§ 参考情報** に記載しています。

## Sink 分析結果

| カテゴリ | 結果 | 根拠 |
|---|---|---|
| SQL Injection | ✅ シンクなし | 全 JPA repository が Spring Data の派生クエリ（`findByOrderId(UUID)` / `findByCustomerId(UUID)` / `findByTrackingId(UUID)` / `findByRestaurantIdAndProductIdIn(UUID, List<UUID>)`）。`@Query` / `nativeQuery` / `JdbcTemplate` / 文字列連結クエリは一切無し |
| Command Injection | ✅ シンクなし | `Runtime.exec` / `ProcessBuilder` の使用なし |
| Path Traversal | ✅ シンクなし | ユーザー入力を伴う `Files.*` / `Paths.get` / `FileInputStream` 等の使用なし |
| Unsafe Deserialization | ✅ シンクなし | `ObjectInputStream` / `XMLDecoder` / Jackson polymorphic typing（`enableDefaultTyping` / `activateDefaultTyping` / `@JsonTypeInfo`）なし。Kafka は Avro `SpecificAvroReader` + Schema Registry |
| XXE | ✅ シンクなし | `DocumentBuilder` / `SAXParser` / `XStream` / `YAMLMapper` の使用なし |
| SSRF | ✅ シンクなし | アウトバウンド HTTP クライアント（`RestTemplate` / `WebClient` / `HttpClient` / `URL.openConnection`）が production コードに存在しない |
| Weak Crypto | ✅ シンクなし | `MessageDigest` / `Cipher` / MD5 / SHA1 / 独自 RNG の使用なし |
| XSS | ✅ 攻撃面なし | JSON-only REST（`application/vnd.api.v1+json`）。Thymeleaf 等のサーバーサイドテンプレートなし |
| CSRF | ✅ 該当せず | セッション/Cookie 認証を採用していないため CSRF の概念が適用されない |
| Mass Assignment | ✅ 問題なし | `CreateOrderCommand` は `customerId`, `restaurantId`, `price`, `items`, `address` のみ。`Order` の `id` / `trackingId` / `orderStatus` / `failureMessages` 等の内部状態はサーバー側（`OrderDataMapper` / `OrderDomainServiceImpl`）で生成・付与されており、外部からの上書き不可 |
| 情報漏洩（エラーレスポンス） | ✅ 問題なし | `OrderGlobalExceptionHandler` は呼び出し元が送信した UUID をエコーするのみ（UUID は推測不可能と見做す）。汎用 `Exception` ハンドラは固定文言 `"Unexpected error!"` を返却 |
| ログ漏洩 | ✅ 問題なし | ログ出力は UUID と Kafka offset のみ。パスワード／トークン／PII の出力なし |

## 個別確認結果

### REST 攻撃面

- `OrderController`: `POST /orders`、`GET /orders/{trackingId}` の 2 エンドポイントのみ
- `payment-service` / `customer-service`: REST コントローラなし（Kafka 駆動）

### Kafka 攻撃面

- 全コンシューマで Avro `SpecificAvroReader` を使用
- Schema Registry によりスキーマ整合性が強制される
- ポリモーフィック JSON 等の危険なデシリアライゼーション経路なし

### 設定ファイル

- `application.yml` 3 ファイルに `password: admin` がハードコードされているが、これはローカル Docker Compose（`infrastructure/docker-compose/pgadminpostgre/postgres.yaml`）の開発用クレデンシャル
- 学習用個人プロジェクトの localhost バインド前提に基づき、レビュー除外ルール（HARD EXCLUSION #2）に該当するため **脆弱性として報告しない**
- 本番／非ローカル環境にデプロイする際は環境変数化が必須

## 参考情報（報告閾値未満・要対処の構造的ギャップ）

### 認証・認可の不在

- `OrderController` の REST エンドポイントには Spring Security が一切設定されていない
- `spring-boot-starter-security` が依存関係に含まれていない
- リクエストボディの `customerId` をサーバーがそのまま信用する構造

**現状の評価:**
- UUID は推測不可能と仮定（レビュー precedent）
- `CLAUDE.md` 上、本プロジェクトは Udemy 講座ハンズオンのローカル学習用と明記
- ローカル `localhost` バインド想定

…という前提のため、**現時点では脆弱性ではなく「デプロイ前に対処すべきアーキテクチャ上のギャップ」** として扱う。

**本番／非ローカル環境にデプロイする前に必須:**
1. Spring Security（または同等の認証フィルタ）の導入
2. `customerId` をリクエストボディから取得するのではなく、認証コンテキスト（JWT サブジェクトや OAuth プリンシパル）から取得するようリファクタ
3. SAGA / Outbox の実装と並行して整備するのが望ましい

## レビュー除外ルール（適用済み）

以下のカテゴリは本レビュー対象外として除外:

- DoS / リソース枯渇
- ローカル開発用クレデンシャルのハードコード（HARD EXCLUSION #2）
- レート制限
- 監査ログの不在
- 古いサードパーティライブラリ
- ユニットテストファイル
- ログ詐称（ユーザー入力をそのままログ出力すること自体は脆弱性ではない）
- パス制御のみの SSRF
- ReDoS / Regex injection
- ドキュメント／Markdown ファイル
- 防御的なハードニング不足（具体的脆弱性のみ報告）

---

## 結論

報告対象（HIGH / MEDIUM × confidence ≥ 8）に該当する脆弱性は **0 件**。

DDD / ヘキサゴナル構成によりユーザー入力が型システムを経由して JPA に到達するため、注入系のシンクが構造的に閉じている。次に対処すべきは「公開デプロイ時の認証・認可レイヤ整備」であり、これは SAGA / Outbox 実装と並行して進めるべき項目。
